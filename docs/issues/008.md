# Issue 8 — Better mobile experience

## Summary

CollabHub works on a phone. Below 768px the sidebar becomes a drawer and the member and thread
panels take the whole screen, and every screen works at 360px wide. Every message, at every
width, gets a "⋯" button that opens its actions — react, reply in thread, edit, delete — which
today appear only on hover, so a touch screen never shows them. The reaction picker closes on
Escape and on a tap outside it.

## Services touched

**The SPA only.** Read `docs/design/06-frontend-spa.md` (no section covers layout, touch or
hover yet — this issue adds one) and :312-314 (the thread panel's place in the layout).

## What exists already

- **No responsive layout at all.** No `sm:`/`md:`/`lg:` class, `@media` rule or `matchMedia`
  anywhere in `src/frontend/src`. The viewport meta is set (`index.html:5`).
- **The shell:** `ChatLayout.tsx:70`, `grid h-full grid-cols-[16rem_1fr]` — a 256px `<aside>`
  (search, workspace switcher, channel list, DM list, create-channel, sign out, connection
  status) and `<main>`. No drawer, no toggle.
- **The right column:** `ChannelView.tsx:93-145` puts `MemberPanel` (`w-64 shrink-0`,
  `MemberPanel.tsx:46`) or, with a thread open, `ThreadPanel` (`w-80 shrink-0`,
  `ThreadPanel.tsx:136-139`) beside the message column (`flex min-w-0 flex-1`). DMs have no
  member panel. At 390px the message column is squeezed to nothing.
- **Hover-only actions:** `MessageItem.tsx:138`, a span with
  `opacity-0 group-hover:opacity-100 focus-within:opacity-100` holding `ReactionPicker`,
  "Reply in thread" (`thread-open`), Edit and Delete, each gated by `canReact`, `canReply`,
  `canEdit`, `canDelete` (:94-102). `ThreadPanel` reuses `MessageItem` for its rows, without
  `onOpenThread`. It is the only hover-revealed control in the SPA.
- **`ReactionPicker.tsx`:** a "React" button (`aria-expanded`, `aria-label="Add a reaction"`)
  toggling an absolutely positioned row of six emoji (`reaction-option`). It closes only on a
  pick or a second click; no Escape, no outside click, no focus handling — and on purpose not on
  blur, which races the option's click (its header :8-12).
- **Always visible already:** `ReactionBar` chips, `ThreadSummary`, the channel header's
  controls, the member panel's remove buttons.
- **Tests:** Vitest clicks the actions by role and passes whatever the CSS (jsdom has none).
  The BDD page object `tests/bdd/pages/chat_page.py` hovers before `react_to` (:322-332) and
  `reply_in_thread` (:362-365). Every Playwright context is `browser.new_context()` with
  defaults (`tests/bdd/conftest.py:257, :328`): desktop viewport, no touch.
- **Register D20** (React Native vs. PWA for mobile) is 🔴.

## Requirements

1. **"⋯" on every message.** Every message that has at least one action — in the channel and in
   the thread panel, at every width — shows a "⋯" button, always visible. It opens a menu of the
   actions that message allows today: React, Reply in thread, Edit, Delete, under the existing
   `can*` rules. A deleted or pending message has none, so it has no "⋯". The hover-revealed row
   is removed.
2. **React from the menu.** "React" opens the six-emoji row; picking one toggles that reaction,
   as the picker does today.
3. **Closing.** The menu and the emoji row close on Escape, on a click or tap outside them, and
   after a choice. Opening one message's menu closes any other.
4. **Accessible.** "⋯" is a menu button (`aria-haspopup`, `aria-expanded`, a label naming what
   it is for). Opening it moves focus into the menu; closing it returns focus to "⋯".
5. **Narrow is below 768px.** Every rule below about "narrow" means a viewport under 768px
   wide; at 768px and over, the layout is today's.
6. **The drawer.** When narrow, the sidebar is a drawer, closed by default, opened by a ☰
   button in the channel header and closed by picking a channel or DM, by a close button, or by
   a tap outside it. With no channel open (first load), the drawer is shown.
7. **Panels take the screen.** When narrow, the member panel and the thread panel each cover the
   message view, with a back or close control that returns to it.
8. **360px works.** At 360px wide, every screen works with no horizontal scrolling: sign-in, the
   channel view and composer, threads, DMs, search, the create-channel and new-DM dialogs, the
   workspace switcher, and attachments (upload, inline image, download). The composer stays
   above the on-screen keyboard.
9. **Crossing the breakpoint** — a rotation or a resize — loses nothing: an open thread stays
   open (side panel ⇄ full screen), the composer's draft and the scroll position are kept, and
   the drawer is closed whenever the width is 768px or more.

## Where the rules meet

- **The menu and the drawer (R3, R6):** opening the drawer closes any open menu; a tap on the
  drawer's backdrop closes the drawer and nothing else.
- **The menu and the thread panel (R1, R7):** a narrow thread panel's rows have the same "⋯";
  "Reply in thread" is not on them, as today.
- **Edit and the menu (R1):** choosing Edit closes the menu and opens the editor in the row;
  Escape in the editor cancels the edit (as today) and does not reopen the menu.
- **A thread opened from a narrow channel (R7, R9):** closing it returns to the channel at the
  scroll position it left.

## Paths each rule holds on

| Path | What must be true |
|---|---|
| First load on a phone, nothing open | the drawer shows the channels; picking one closes it |
| Open a DM from the drawer | the DM fills the screen; ☰ is there to go back |
| A message from someone else, on touch | "⋯" offers React and Reply only |
| Your own message | "⋯" offers React, Reply, Edit, Delete |
| Keyboard only, desktop | Tab reaches "⋯", Enter opens it, every item can be reached and chosen from the keyboard, Escape closes and focus returns to "⋯" |
| Rotate with a thread open | the thread stays open, in its new form |
| Search on a phone, then jump to a result | the channel opens at the message, drawer closed |
| Composer focused, keyboard up | the composer is visible above it |

## What this assumes — check before building on it

- **`100dvh` (or `interactive-widget=resizes-content` in the viewport meta) keeps the composer
  above the on-screen keyboard** on current iOS Safari and Android Chrome. Check both; this is
  the R8 rule most likely to need a different mechanism.
- **jsdom evaluates no media queries.** "Narrow" must come from something a Vitest test can set —
  one `useIsNarrow` hook over `matchMedia`, for example, stubbed in tests — and the layout must
  read it from there, not only from CSS classes.
- **Playwright's touch emulation** (`has_touch`, `is_mobile`, a 390×844 viewport) is enough for
  the BDD journey to tap "⋯" and the drawer. Real devices are the acceptance run.

## Timing

n/a — there is no throttle, window or race in this issue. Menus open and close on events.

## Decided already

1. One "⋯" menu at every width; the hover row is removed everywhere.
2. The breakpoint is 768px (Tailwind `md`).
3. The reaction picker's missing Escape and outside-click close come into this issue.
4. Responsive web only. **D20 stays 🔴 and untouched**: no PWA manifest, no service worker, no
   native app. This issue makes no choice between them.
5. Light palette only, as D26/D28 have it.

Left to the plan, on purpose: the menu's markup and keyboard model beyond R4, how "narrow" is
computed, the drawer's animation, and the icons.

## Tests

- **Vitest:** the menu's items per message under each `can*` rule; Escape, outside click and a
  choice each close it; focus in and back; one menu open at a time; the picker's closing; the
  drawer and panels under a stubbed narrow flag; crossing the breakpoint keeps the thread open
  and the draft.
- **One BDD journey on a touch phone viewport:** Ada, on a 390×844 touch context, opens the
  drawer, picks #general, reacts to Grace's message through "⋯", and replies in its thread.
- **The page objects change:** `react_to`, `reply_in_thread`, edit and delete open "⋯" instead
  of hovering. Every existing journey must still pass.

## Record in this slice

- Doc 06: a new section on layout below 768px, the drawer, the panels, and the "⋯" menu.
- Register: a new entry **D46 🟢** — responsive web below 768px, actions behind "⋯" — noting
  that it leaves D20 open.
- An ADR: one menu at every width rather than hover on desktop and something else on touch.

## Not in this issue

- A PWA, a service worker, offline, a native app (D20).
- Swipe gestures, pull to refresh, haptics.
- Dark mode or any per-user setting (D28).
- A layout for large tablets beyond what 768px+ already is.

## Acceptance — first real run, on a phone, through a preview

`scripts/deploy.sh preview up` on the branch; Ada on a real phone, Grace on a laptop:
- Ada's first screen is the channel list; she picks #general and it fills the screen.
- Grace posts; Ada taps "⋯" on it, reacts, and replies in the thread; Grace sees both live.
- Ada focuses the composer: it stays above the keyboard. She attaches a photo and sends it.
- Ada rotates the phone with the thread open: it stays open.
- On the laptop, Grace uses "⋯" with the keyboard only; Escape closes it.
